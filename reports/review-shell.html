S-Base / Product & engineering review / 19 October 2026

Make everyday actions feel trustworthy.

S-Base already has the breadth of a personal power tool. The next improvement should be confidence: edits that survive interruption, charts that tell the truth, actions that explain their outcome, and access rules that match ownership. Prioritize workouts, recipes, measurements and wines, while closing the cross-user access gaps before expanding the product.

Reliability first; useful depth next

01 · Protect work and boundaries

Resolve Cashflow/Minor ownership checks (PM01). Then protect workout sync and durable local saves (D07–08), transactional recipe saves (D02), truthful measurement charts (D04), and consistent session expiry (PL05).

02 · Make daily actions predictable

Fix clearing recipe fields, failed quick actions, editing-mode ambiguity and photo deletion. Repair scoped search, authentication recovery and keyboard/touch controls. Use the same draft/error patterns in invoices, Minor and Resume.

03 · Add only useful depth

Try a small cooking mode before meal planning. Decide notebook versus cellar before wine inventory. Add measurement date ranges before trend models. Keep administration narrow, recoverable and clear about live state.

What this review proves—and what remains to test

Scope: read-only inspection of the current working tree on 19 October 2026, across frontend interactions, backend services and routes. Existing uncommitted edits were present, including workout files. References describe that snapshot and may move as code changes. This is a product/engineering review, not a full security, accessibility or compliance certification.

Evidence labels: “Source verified” means the stated implementation was read; the resulting user scenario is reasoned from that code unless explicitly reproduced. “Runtime checked + source” applies to the observed unauthenticated destination/query loss only. “Isolated check + source” applies to the session timestamp comparison reproduced with SQLite literals in memory. “Opportunity” means a product choice informed by existing behavior and competitor patterns, not a defect.

Runtime boundaries: the frontend-only preview used a deliberately unavailable backend. Login rendering and an unauthenticated redirect were inspected. No authenticated save, live permission change, public publishing, production Cloudflare flow, server restart, update or backup was exercised. No real user data was mutated. Timing races, multi-user access scenarios and failures need synthetic isolated tests. Temporary preview configuration/cache changes were removed by the researcher; no application edits are part of this report.

Unresolved product choices: wines/recipes may intentionally be shared; confirm the intended rights model. External Minecraft backups may already exist. Publishing may be disabled locally. Competitor documentation was reviewed without paid accounts or hands-on usability trials. Withings evidence is weaker and explicitly marked. No mobile touch session, screen-reader session, measured contrast audit, PDF text extraction, load test or user interview was performed.

Preserve: Dutch UI, the Signal Panel visual language, focus rings, reduced-motion support, skip link, session/module guards, paused-account denial and existing credential/cookie protections. These foundations are valuable; the proposed work is consistency and reliability. This standalone review uses system fonts to remain self-contained; it does not propose changing product typography.

Implementation gate: agree the shortlist and intended behavior separately. Any future schema changes require non-destructive migrations. Test with isolated synthetic data; never reset or seed the custom development database. Keep the external Minor website outside implementation scope unless separately approved.
