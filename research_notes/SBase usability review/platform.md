# Platform, Pulse and Minecraft audit

## How does shared interaction behave?

### Takeaway
The largest shared UX gap is unreliable context and state communication: global search silently means recipes almost everywhere, authentication loses the user's destination, and small custom controls do not consistently meet the project's own accessibility requirements. Findings below are source-verified unless explicitly marked runtime-verified. Priority P1 means address before expansion, P2 means next usability iteration; effort S/M/L means small/moderate/substantial, not a time estimate.

### Cited Findings

**PL01 — Search must match the user's current module (P1, M).** On Pulse, Cashflow, Minor, Resume or Minecraft, opening header search and entering a term calls recipe suggestions and submitting goes to `/recipes`. Only workouts have a separate path. This is a concrete surprising navigation behavior, not a proposed missing feature. [Search routing](../../frontend/src/components/search-bar.tsx:32), [submission](../../frontend/src/components/search-bar.tsx:131), [always mounted](../../frontend/src/components/nav-header.tsx:163). Recommended option: module-scoped search with visible scope and clear results/empty/error states; hide it in modules without meaningful search. Alternative: explicit cross-module command palette, permission-filtered results and keyboard shortcut. Also cancel/ignore stale suggestion requests (current debounce cancels timers only). Acceptance: search from every module stays in declared scope; no forbidden-module requests; slower old response cannot replace new query results; screen reader gets combobox/listbox/active-option semantics.

**PL02 — Account menu needs a complete keyboard/mobile contract (P1, S).** The trigger advertises a menu, but rendered popup is a generic div; no Escape handler, arrow navigation, focus transfer/return. On narrow screens its only text is CSS-hidden and icons have no explicit accessible trigger label. Clicking outside closes it; keyboard behavior lacks parity. [Menu](../../frontend/src/components/nav-header.tsx:165), [outside handler](../../frontend/src/components/nav-header.tsx:52). W3C menu-button pattern expects menu semantics and focus into first item on activation. [W3C](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/). Recommended: existing accessible menu primitive. Alternative: simple disclosure with ordinary links/buttons and appropriate disclosure semantics, no menu promise. Acceptance: named trigger at 320px; Tab/Enter/Escape functional; predictable focus return; no keyboard trap.

**PL03 — Touch sizing contradicts the design contract (P2, M).** Base button sizes are 24–36px high, search trigger 36px and login controls 40px. There is no coarse-pointer size override in the inspected stylesheet. These violate DESIGN.md's own 44×44 mobile rule; do not call every one an automatic WCAG AA violation, since AA target-size exceptions/spacing differ. [Button variants](../../frontend/src/components/ui/button.tsx:22), [search](../../frontend/src/components/search-bar.tsx:223), [login](../../frontend/src/components/login-form.tsx:47), [design](../../DESIGN.md). Recommended: 44px hit regions on coarse pointers/mobile while retaining compact visual density on desktop. Alternative: user-selectable compact/comfortable density with mobile minimum enforced. Acceptance: inspect actual bounding boxes at 320/375/768px, adjacent targets do not overlap, keyboard focus remains visible. Login visual inspected at desktop; mobile geometry not runtime-tested.

**PL04 — Authentication should resume the task and explain recovery (P1, M).** Runtime-verified: unauthenticated navigation to `/recipes?q=synthetic-audit` redirected to bare `/`, losing destination/query. Source: local login always goes to dashboard; proxy Cloudflare exchange preserves pathname only; central API throws raw error but has no shared 401 recovery; server current-user fetch maps every exception including outage to null. Production hides logout entirely. Cloudflare exchange treats every 403 (including account paused) as 'Geen account gevonden'. [Proxy](../../frontend/src/proxy.ts:5), [login](../../frontend/src/components/login-form.tsx:25), [API](../../frontend/src/lib/api/core.ts:23), [server identity](../../frontend/src/lib/server-api.ts:36), [production logout](../../frontend/src/components/nav-header.tsx:208), [CF denial](../../frontend/src/app/api/auth/cf-exchange/route.ts:35). Recommended: typed auth/offline/permission states, safe same-origin returnTo including query, preserve drafts before reauthentication, explicit Cloudflare-aware sign-out/account switching. Alternative: central session-expired dialog that resumes the current action after login. Acceptance: expiry during form entry loses no draft; outage shows retry rather than credential error; paused/no-account distinct; successful reauth restores route+filters; test actual Cloudflare production flow separately. Do not infer frontend proxy omission is an authorization bypass: backend guards exist.

**PL05 — Session expiry compares incompatible timestamp formats (P1, S).** Backend stores ISO timestamps with `T` but compares text to SQLite `CURRENT_TIMESTAMP` with a space. [creation/comparison](../../backend/src/auth/index.ts:49). Verified separately using in-memory SQLite literals: `'2026-10-19T08:00:00.000Z' > '2026-10-19 18:00:00'` returns 1, while comparing their julianday values returns 0. Server-side validation can accept a timestamp already expired earlier that UTC day; normal browser cookie expiry limits the visible effect but does not repair server validation. Recommended: compare same ISO-format UTC value or numeric epoch consistently across all session methods. Alternative: migrate to numeric epoch with non-destructive migration. Acceptance: at exact expiry invalid, just before valid, around UTC midnight consistent; existing records remain usable until their real expiry; no live DB modification for verification.

### Inferences
- A persistent module switcher and optional command palette would reduce repeated dashboard round trips; this is an enhancement hypothesis, not a demonstrated user-research result. Begin by fixing misleading search.
- Shared status/error/draft patterns would benefit more tasks than purely aesthetic redesign. No blanket offline support recommendation: admin/server operations need connectivity and truthful status.

### Gaps
No authenticated app session or production Cloudflare session was used. Runtime covered rendered login and unauthenticated redirect only. Login had readable visual placeholders and Dutch content; persistent visible labels/autocomplete/error announcement merit improvement from source (login-form.tsx:40–63). No mobile, screen-reader, actual save, expiry or permission mutation was executed.

## Are administration and server operations safe and understandable?

### Takeaway
Pulse already has stronger interaction primitives than the shared shell (44px controls, status announcements, explicit system confirmation). It needs protection against lockout and durable operation state. Minecraft's polling and lifecycle controls need clearer distinctions among unknown, offline, changing and failed states.

### Cited Findings

**PL06 — Protect the last administrator and make permission changes atomic (P1, M).** A Pulse user can click Pause on self (only impersonation hides for self) or remove own Pulse permission; backend receives target ID and applies directly, with no last-active-admin invariant. Permission replacement deletes rows then inserts without a transaction. [self actions](../../frontend/src/app/pulse/user-row.tsx:229), [route](../../backend/src/routes/pulse.ts:50), [service](../../backend/src/modules/pulse/index.ts:106). Scenario: sole administrator pauses self or removes Pulse, loses admin UI and needs CLI recovery; insertion failure can leave partially removed permissions. Recommended: enforce at least one active Pulse administrator server-side, transactional update and explicit consequence confirmation; retain CLI break-glass recovery. Alternative: forbid self-revocation/pause entirely. Acceptance: direct API as well as UI blocks final-admin removal; second admin can change first; failures rollback full permission set; clear actionable errors. Also use per-user pending state rather than one global loadingUserId for overlapping row operations (client.tsx:49,99–154).

**PL07 — Honor Minecraft read boundaries, not just write boundaries (P1, M).** Middleware checks assigned slug for `/servers/:slug`, then returns immediately for any GET. Therefore monitor-role users can reach unscoped GET `/import/scan`, `/templates`, template metadata and template file lists, though writes require full access. [route guard](../../backend/src/routes/minecraft.ts:8), [template endpoints](../../backend/src/routes/minecraft.ts:163). This is a verified policy inconsistency; the sensitivity of returned metadata depends on deployment. Recommended: explicit capability matrix, default-deny admin reads, server-specific scopes; return UI capabilities from backend. Alternative: simpler monitor vs operator vs administrator roles. Acceptance: assigned monitor sees only intended server resources, cannot enumerate imports/global templates; UI and direct API agree; unauthorized and nonexistent states do not conflate. Pterodactyl documents separate console, power, file, backup and schedule capabilities rather than one global full-access toggle. [Pterodactyl permissions](https://docs.pterodactyl.io/v1/api/client-general/get-show-permissions).

**PL08 — Show stale/disconnected status instead of false certainty (P1, M).** Minecraft defaults status to offline, ignores polling failures, turns initial request errors into Not Found, and file-list failures into empty arrays. Polls run every 5s with no in-flight overlap guard. [status/poll](../../frontend/src/app/games/minecraft/[slug]/page.tsx:32), [failure](../../frontend/src/app/games/minecraft/[slug]/page.tsx:97), [file list](../../frontend/src/app/games/minecraft/[slug]/files/page.tsx:50). Scenario: tunnel drops while server was online; screen retains online indefinitely, or new page says missing/empty, encouraging wrong actions. Recommended: last-success timestamp, stale badge, retry, distinguish 401/403/404/network, non-overlapping polling with backoff and hidden-tab pause. Alternative: SSE/WebSocket with fallback polling; more effort, not prerequisite. Acceptance: network cut shows unknown/stale within bounded interval; never represents failed file fetch as genuinely empty; retry restores state without full reload; only one poll in flight.

**PL09 — Server stop/restart needs consequence preview and durable phases (P1, M/L).** Stop/restart buttons dispatch immediately. Backend graceful stop escalates after 20s to TERM then KILL; UI communicates only a spinner, and backend returns ok even after forced path. [buttons](../../frontend/src/app/games/minecraft/[slug]/page.tsx:285), [action handler](../../frontend/src/app/games/minecraft/[slug]/page.tsx:141), [backend](../../backend/src/modules/minecraft/lifecycle.ts:146). Scenario: restart with players connected interrupts session; slow world save becomes force termination without the operator being informed. Recommended: confirm showing server/player count, announce/countdown option, job states saving/stopping/starting/ready/failed and report graceful vs forced outcome. Alternative: explicit separate force-stop requiring stronger confirmation; preserve configurable automated escalation for unattended policy. Acceptance: duplicate clicks do not create duplicate operations; reconnect recovers job; no 'ready' until readiness probe succeeds; UI warns if forced termination occurred.

**PL10 — Pulse updates/reboots need history and reconnect outcome (P2, M/L).** Update UI polls only while status running and silently swallows errors. Reboot stores local `rebootRequested` flag, without a reconnection state machine. Service holds current update state in process memory (class, inspect alongside source), so durable historical evidence is absent from this flow. [polling](../../frontend/src/app/pulse/system-panel.tsx:74), [reboot](../../frontend/src/app/pulse/system-panel.tsx:177), [service](../../backend/src/modules/pulse/system-update-service.ts:119). Recommended: durable operation ID/history, last status timestamp, expected disconnect notice, health polling/backoff, final verification after return. Alternative: keep Pulse lightweight and deep-link to Cockpit for OS maintenance. Cockpit source shows update history, success state and reboot/service-restart choices. [Cockpit update implementation](https://github.com/cockpit-project/cockpit/blob/main/pkg/packagekit/updates.jsx). Acceptance: reload mid-operation reconnects to same job, backend restart doesn't erase last result, timeout has a recovery action, no success claim merely because reboot request was accepted.

**PL11 — Preserve actionable errors until resolved (P2, S/M).** Pulse dismisses success and error messages alike after 3s, while mutations use generic failure text. Minecraft uses native alert/prompt/confirm for several actions. [Pulse notifications](../../frontend/src/app/pulse/client.tsx:58), [Minecraft actions](../../frontend/src/app/games/minecraft/[slug]/page.tsx:141). Recommended: shared inline errors bound to affected control plus optional notification, persistent until dismissed/retried; distinguish validation, permission, session, connectivity and server failure with user action. Alternative: persistent notification center for admin jobs, inline errors for forms. Acceptance: error remains readable after 10s; retry preserves input; correct live-region announcement; keyboard focus restored after dialogs. Avoid confirmations for every reversible action: reserve for consequence-changing operations.

**PL12 — Add verified backup/restore workflow before more server features (P2, L).** Reviewed Minecraft routes expose lifecycle/files/templates/import/player operations but no backup/restore endpoint; searching module/frontend for backup returned no matches. Templates are not a verified recovery workflow. [Minecraft routes](../../backend/src/routes/minecraft.ts:4). This is a scoped feature-gap finding, not proof no external backup system exists. Recommended: on-demand and scheduled world backup with last-success age, retention and tested restore; dry-run metadata and restore to new instance first. Alternative: integrate existing external backup system and surface status/recovery instructions; do not duplicate infrastructure unnecessarily. Pterodactyl explicitly models backup create/read/delete/download and server schedules. [Pterodactyl permissions](https://docs.pterodactyl.io/v1/api/client-general/get-show-permissions). Acceptance: a synthetic world restores to a separate instance, backup failures surfaced, operators see restore consequences and available recovery points, no overwrite without confirmation.

### Inferences
- Prefer fixing existing reliability/access problems over adding charts or more settings. Cockpit integration is an option if OS administration is incidental to S-Base; replacing custom Minecraft entirely is not necessary to gain role granularity and safer recovery.
- A compact activity log for permission and server-power changes would make support investigations easier. Treat this as an enhancement requiring retention/privacy choices, not a demonstrated compliance requirement.

### Gaps
No live server stop/start, user permission change, update, reboot, upload or backup was attempted. Backend source behavior is verified, but no exploitation or production exposure assertion is made. External backup infrastructure and intended monitor-role scope require owner confirmation before implementation.

## What was tested and what should be retained?

### Takeaway
The repository already contains useful foundations. Improve consistency rather than replace the design system or add heavyweight features everywhere.

### Cited Findings
- Backend module guards check session and module permissions; paused accounts are denied. [Auth plugin](../../backend/src/context.ts:48), [session](../../backend/src/auth/index.ts:89).
- Security foundations include credential hashing, rate-limited login, HttpOnly/SameSite cookies, production secure cookies and production-safe generic server errors. [Login](../../backend/src/routes/auth.ts:7), [error handler](../../backend/src/index.ts:30). These strengths do not constitute a comprehensive security audit.
- Pulse has semantic sections, a polite status region, search label and 44px controls; system changes use accessible alert-dialog primitives and running-update conflict handling. [Pulse](../../frontend/src/app/pulse/client.tsx:186), [system dialog imports](../../frontend/src/app/pulse/system-panel.tsx:21).
- Shared skip link, document lang=nl, focus rings and reduced-motion stylesheet exist. [Header](../../frontend/src/components/nav-header.tsx:92), [root](../../frontend/src/app/layout.tsx:17), [motion](../../frontend/src/app/globals.css:384).
- Minecraft console preserves the user's scroll position when reading older log lines. [scroll behavior](../../frontend/src/app/games/minecraft/[slug]/page.tsx:128).

### Inferences
Keep Dutch UI, tonal dark surfaces, compact desktop density and gradual disclosure. Power-tool behavior means trustworthy state, recoverable actions, fast navigation and predictable keyboard support, not maximum feature count.

### Gaps
Runtime record (2026-10-19): initial browser localhost:3000 refused connection. Started frontend only on loopback 3099 with API_URL pointed to deliberately unavailable 3999, no backend/database start, no sign-in/form submission. Visually inspected login and its DOM. Navigated unauthenticated recipes query URL and observed bare-root redirect. Stopped preview afterward. Next automatically added two temporary tsconfig includes and generated a frontend/tmp cache despite requested absolute distDir; exact added includes were removed (git diff for tsconfig empty), owned generated cache moved to /tmp and empty owned directory removed. No application edits remain; existing dirty tree preserved. Independent Python SQLite in-memory literal comparison verified timestamp-format behavior. No tests of authenticated application behavior, production Fedora/cloudflared networking, mobile touch, real assistive technology or load/performance. All other interaction scenarios are code-derived and must be labeled accordingly in final report. Competitor comparison used official online documentation/source, not hands-on comparative trials.
