# Recipes, Workouts, Measurements and Wines

## What breaks or makes interactions harder today?

### Takeaway
Preserve the substantial workout capabilities already present. Prioritize reliable saves, truthful charts, explicit destructive actions and consistent accessible controls before adding broader planning or social features. This is a read-only code audit of the current working tree on 2026-10-19, not a claim of browser reproduction; several workout files have pre-existing modifications.

### Cited Findings
All source paths below are repository-relative; paths are relative to the repository root. Priorities: P1 = fix first, P2 = improve next, P3 = optional. Effort is relative S/M/L, not a delivery estimate.

1. **D01 — Recipe fields cannot actually be cleared. Confirmed code defect; P1/S.** Clear an existing description, kitchen or cooking time, save, and the old value is retained: the form sends `undefined`, and update uses nullish fallback to existing values. No runtime reproduction performed. [form:134](../../frontend/src/components/recipe-form.tsx#L134), [service:188](../../backend/src/modules/recipes/index.ts#L188). Minimal/recommended: explicit nullable patch fields, with omitted meaning unchanged and null meaning clear. Broader option: shared validated edit schema and dirty-field patches. Acceptance: clear each optional field, reload, see blank; untouched fields remain unchanged. Recipe rating only offers 1–10 and no clear control despite backend accepting 0–10; include explicit Unrated and 0 if the product promises 0–10 [detail:175](../../frontend/src/components/recipe-detail.tsx#L175), [service:251](../../backend/src/modules/recipes/index.ts#L251).

2. **D02 — Failed recipe saves can partially change the recipe. Confirmed code defect; P1/M.** Create inserts the parent before checking ingredient quantity; update writes parent and deletes existing ingredients before checking replacement quantities. Neither service nor direct route caller wraps these operations in a transaction. A malformed API payload or insertion failure can leave partial data while UI says save failed. This is especially relevant to future import features, even though the present form checks positive quantities. [service:113–234](../../backend/src/modules/recipes/index.ts#L113), [routes:39–40](../../backend/src/routes/recipes.ts#L39). Recommended: validate the complete input before writes and transactionally replace related rows. Broader: shared request schemas, structured field errors, transactional service boundary. Acceptance: an invalid second ingredient or injected failure leaves all prior fields, steps and ingredients unchanged; invalid create leaves no recipe row. Invalid rating/status should be a proper 4xx, not a returned Error object [service:245](../../backend/src/modules/recipes/index.ts#L245).

3. **D03 — Quick actions need visible saving/error states. Confirmed code behavior; P1/S–M.** Recipe status/rating/delete await calls without catch or pending state; delete dialog closes before the request. Wine delete catches only to console and dismisses confirmation. On a timeout or access expiry the user lacks a clear explanation or retry. [recipe detail:54–68,150](../../frontend/src/components/recipe-detail.tsx#L54), [wine card:65](../../frontend/src/app/recipes/wines/wine-card.tsx#L65). Recommended: one pending action, inline error and retry, keep destructive dialog open until confirmed success. Broader: consistent mutation-feedback primitive with optimistic rollback for reversible rating/status changes. Acceptance: simulated 403/500/offline yields readable localized error, preserves current value, and prevents double submission. No need for global toast spam on every successful click.

4. **D04 — Body chart turns missing muscle values into zero and compresses irregular time. Confirmed code defect; P1/M.** Mass tab includes logs with either muscle or fat mass; missing muscle is then plotted as zero. Every row gets equal x spacing regardless of dates. A fat-only entry can appear as a sudden muscle collapse; one day and one month appear equally far apart. [chart:7–15,41–74](../../frontend/src/app/workouts/body/body-chart.tsx#L41). Recommended: independent nullable series, real elapsed-time x scale, no fabricated zero, labels explain gaps. Broader: date-range controls, optional clearly labelled trend smoothing, table alternative. Acceptance: synthetic Jan 1/2/31 records have proportional spacing; fat-only entries never imply muscle=0; a one-point series is understandable. Tooltips are hover-only SVG groups with no keyboard target [chart:96–145](../../frontend/src/app/workouts/body/body-chart.tsx#L96): provide keyboard/touch details and accessible data summary.

5. **D05 — Measurement editing can silently switch or replace the user's draft. Confirmed code behavior, impact inferred; P2/M.** Editing another row directly replaces shared form state; New while editing also replaces it. During creation, changing date to one with an existing log silently populates its values while editingId stays 0; save is a backend upsert. This may be convenient, but the interface should tell users whether they are creating or updating. [body page:115–151](../../frontend/src/app/workouts/body/page.tsx#L115), [measurement service:146–177](../../backend/src/modules/measurements/index.ts#L146). Recommended: label 'Edit existing measurement for this date', protect dirty form before switching rows/dates. Alternative: strict create with collision link to edit; more predictable, one extra step. Acceptance: changing to an existing date announces edit mode; switching away from unsaved input offers keep/discard, and collision cannot quietly overwrite another day's values.

6. **D06 — Photo removal is immediate and permanent. Confirmed code behavior; P2/M.** Small thumbnail X calls delete directly without confirmation/undo; backend deletes record then physical file. Full measurement deletion correctly has confirmation, so photo behavior is inconsistent. [body card:165](../../frontend/src/app/workouts/body/body-log-card.tsx#L165), [upload hook:65](../../frontend/src/app/workouts/body/use-photo-upload.ts#L65), [measurement service:267 onward](../../backend/src/modules/measurements/index.ts#L267), [body page:385](../../frontend/src/app/workouts/body/page.tsx#L385). Minimal: preview plus confirmation; broader: delayed deletion with Undo and server retention policy (requires migration/storage policy). Acceptance: accidental removal can be cancelled or undone; failed delete leaves thumbnail and an actionable message. Avoid physical removal before undo window expires.

7. **D07 — Offline workout acknowledgement can clear newer local work. Confirmed unguarded code paths, race impact requires controlled reproduction; P1/M–L.** `syncOfflineSession` reads a snapshot, awaits server writes, then clears the storage key unconditionally, without checking `updatedAt` against newer edits. Global 15s sync and session sync coexist. Title save also clears the whole session snapshot after a title-only request, outside the exercise promise queue. The exercise queue's local version check is a good safeguard, but does not encompass these other paths. [offline:307–337,367 onward](../../frontend/src/lib/offline-workout.ts#L307), [session sync:60–97,148–166](../../frontend/src/components/use-session-sync.ts#L60). Recommended: one per-session sync coordinator and compare revision before acknowledging/deleting cache; serialize title/pause/exercise/complete through it. Broader: server revision/conflict detection for multi-device edits. Acceptance: delay snapshot A response, write local B, then resolve A; B remains pending and ultimately reaches server. Repeat across title change, pause, finish, background timer and two tabs.

8. **D08 — 'Saved locally' must mean durable storage succeeded. Confirmed code defect risk; P1/M.** `saveOfflineSession` returns void and swallows storage failure with console logging. Finish path unconditionally offers savedLocally after network failure, so quota/security errors could produce an inaccurate promise. [offline:138–159](../../frontend/src/lib/offline-workout.ts#L138), [finish:257–286](../../frontend/src/components/use-session-finish.ts#L257). Recommended: return verified persistence result and show blocking 'not saved' recovery with copy/export current workout, retaining in-memory state. Broader: IndexedDB transactional queue (still handle write failure). Acceptance: forced storage exception plus network outage must never display saved locally; recovery export preserves all sets. Existing rejected-sync UI is valuable and should remain [provider:51–119](../../frontend/src/components/offline-sync-provider.tsx#L51).

9. **D09 — Apply accessibility fixes to the actual dense controls. Confirmed markup facts; P2/M.** Recipe rating controls are 32px, wine edit/delete 32px; these miss repo's 44px tap target requirement. Recipe selected state is only visual (no radio/pressed semantics). Measurement labels are siblings without `htmlFor` or matching ids; chart values are hover-only. [recipe detail:175–211](../../frontend/src/components/recipe-detail.tsx#L175), [wine card:94,131](../../frontend/src/app/recipes/wines/wine-card.tsx#L94), [body edit:62–86,122](../../frontend/src/app/workouts/body/body-edit-card.tsx#L62). Recommended: 44px hit areas, proper radio group or aria-pressed, associated labels and persistent units, keyboard/touch chart access. Alternative: compact desktop visuals with larger invisible hit regions where spacing permits. Acceptance: keyboard-only completion and screen-reader announced label/unit/current rating; 320px layout without horizontal overflow. Don't claim a full WCAG certification from this review.

10. **D10 — Make Wines' sharing/permission model explicit before expanding it. Confirmed code facts; product intent unresolved; P1 decision / M implementation.** Wines store userId but `list(_userId)` ignores it and get/update/delete only use wineId. All wine routes use recipeAuth (`recipes` permission), not a wine permission. Recipes are global too. This might be an intentional household collection, so it is not automatically a security defect; users need an explicit shared-library model if it is intentional. [wine service:21,59,112,154](../../backend/src/modules/wines/index.ts#L21), [routes:50–81](../../backend/src/routes/recipes.ts#L50), [context:83](../../backend/src/context.ts#L83), [schema:5](../../backend/src/db/schema/wines.ts#L5). Option A: preserve shared collection, label it and define contributor/editor rights. Option B: private-by-default user ownership enforced on every list/read/mutation plus explicit sharing (more migration work). Acceptance: a two-user permission matrix has deliberate outcomes for read/edit/delete and UI communicates them. Root agent should combine with its broader authorization audit.

### Inferences
The likely user effects above follow from code, not observed usability sessions. D07 requires timing-controlled tests; D10 requires a product decision. Recipe/wine long forms have state-only editing without draft persistence in their components, whereas workout templates already restore/version-check drafts; a reusable guarded-draft pattern is sensible if users frequently abandon long entry sessions [recipe form:38 onward](../../frontend/src/components/recipe-form.tsx#L38), [wine form:33 onward](../../frontend/src/app/recipes/wines/wine-form.tsx#L33), [template form:79–116](../../frontend/src/components/workout-template-form.tsx#L79).

### Gaps
No production or live browser interactions performed; no personal data read; no mutations, tests, seed or database commands run. No dedicated workout failure reproduction. No screen-reader or measured contrast audit. Caller routes for recipes were read in full, confirming no transaction wrapper there. Existing dirty changes were preserved.

## Which competitor patterns are worth adopting?

### Takeaway
Use competitors as examples of useful interaction patterns, not a feature checklist. Cooking assistance is a strong gap; workout fundamentals already match many specialist-app patterns. Wine inventory is optional until its intended purpose is settled.

### Cited Findings
11. **D11 — Add a focused cooking mode. Opportunity; P2/M.** Current recipe detail renders a static ingredient table and numbered paragraphs [detail:218–292](../../frontend/src/components/recipe-detail.tsx#L218). Paprika documents ingredient crossing-off, highlighted current step, keep-screen-on, timers and scaling [official Paprika](https://www.paprikaapp.com/), checked 2026-10-19. Recommended small version: checklist ingredients, highlight step, reset progress, optional wake lock. Broader version: base servings plus portion scaling and multiple timers; requires explicit unit/scaling rules and schema migration. Acceptance: cook hands-busy on mobile, resume current step, never mutate base ingredient amounts when scaling. Save progress per recipe locally and communicate device-only state. Defer meal planning until cooking flow works.

12. **D12 — Speed recipe capture only after atomic saves. Opportunity; P3/L.** Recipe form is manual entry [form:38–165](../../frontend/src/components/recipe-form.tsx#L38); Paprika documents web import and combining grocery ingredients [official](https://www.paprikaapp.com/). Option A/recommended first: paste/import preview with editable ingredients and source URL. Option B: weekly meal plan and grocery aggregation if recurring planning is a real user need; adds substantial complexity (units, duplicates, pantry). Acceptance: import is reviewable before saving, errors never create partial recipes, unsupported units remain explicit. Dependency D02. Avoid auto-saving scraped content or building a social recipe platform.

13. **D13 — Decide whether Wines is a tasting notebook or cellar inventory. Opportunity; P3/M–L.** Current schema has brand/type/grape/vintage/region/purchase location/rating/notes/photo but no bottle quantity, storage location, consumption events or tasting history [schema:5–18](../../backend/src/db/schema/wines.ts#L5). CellarTracker documents bottle-level tracking, purchases, consumption and drinking windows [official tracking guide](https://support.cellartracker.com/article/32-what-can-be-tracked), [ready-to-drink report](https://support.cellartracker.com/article/28-ready-to-drink-report), checked 2026-10-19. Option A/recommended unless real cellar need: lightweight tasting notebook with repeat tasting entries and 'buy again'. Option B: quantity + consume/undo + location, transaction-backed stock history; optional user-entered drinking window later. Acceptance: drinking a bottle preserves tasting history, stock never negative, undo restores count. Avoid AI sommelier/social marketplace without demonstrated value. Quick win independently: filtered empty states incorrectly say recipes/status and invite 'first wine' even when filter merely has no results; show wines/type and Clear filters [wine page:136–145](../../frontend/src/app/recipes/wines/page.tsx#L136).

14. **D14 — Improve measurement interpretation without creating a medical product. Opportunity; P2/M.** Current chart has four metric tabs and no date-range selector [body page:333–358](../../frontend/src/app/workouts/body/page.tsx#L333). Withings official search result describes a moving-average weight trend [official support](https://support.withings.com/hc/en-us/articles/202720528-How-can-I-see-my-weight-fat-mass-and-BMI-on-the-Health-Mate-app-); full-page fetch failed, so treat this comparator as lower-confidence than the others. Option A/recommended: period selection, latest/change summary, raw points with accurate dates and missing-value behavior (D04 first). Option B: optional labelled smoothed trend and side-by-side photo comparison. Acceptance: users can distinguish a raw record from a trend; sparse data shows insufficient data rather than a misleading trend. Do not copy health scoring or prescriptive targets.

- **Workouts: preserve, refine, do not duplicate.** Hevy explicitly displays previous values, allows tap-to-copy, and distinguishes last exercise performance from last performance in the same routine [official previous values](https://www.hevyapp.com/features/track-exercises/). S-Base already has previous sets, exercise history modal, rest and repetition timers, wake lock, pause/resume, completion summary, offline rejection recovery and template draft recovery [live component:70–77,125–187](../../frontend/src/components/workout-session-live.tsx#L70), [sets table:150](../../frontend/src/components/workout-sets-table.tsx#L150), [template:79–127](../../frontend/src/components/workout-template-form.tsx#L79). Recommend clarifying provenance of suggestions and proving save/complete reliability before adding social feeds, coaching or wearables. Hevy automatic rest timer is also documented [official timer](https://www.hevyapp.com/features/workout-rest-timer/); this is parity to preserve, not a missing feature claim.

### Inferences
Highest-value sequence: fix correctness and saving (D01–04,D07–08), then predictable editing/accessibility (D05–06,D09), then evaluate cooking mode and capture (D11–12). Decide D10/D13 with the owner before designing wine schema changes. Competitive features demonstrate possibilities, not evidence that S-Base users demand them.

### Gaps
No paid competitor accounts or direct hands-on trials. Feature claims come from official public pages, not independent performance evidence. Withings full article was inaccessible; no claims about its overall UX quality. No exact price or market-share claims researched.
